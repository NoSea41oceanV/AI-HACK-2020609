## 1. 目的と利用者

飼い主が登録した犬の情報をAIで構造化し、スタッフが明示選択した当日対象犬の全ペアを採点して、安全制約と施設の部屋設定を満たす部屋割りを提案する。選択中スタッフが最新未確定案を確認し、承認または却下する。観測後は再計算し、操作の対象・担当・日時・理由・元案を追跡できるようにする。

画面はPawPalsモックの構造・配色・操作感を基準とする。表示する数値・分析・履歴は実装・保存・生成済みの実データに限る。将来機能は未対応またはIFと明記する。

施設はFirebase Authでログインし、有効なスタッフを選択する。飼い主はスタッフ発行の招待URLから登録する。施設・スタッフ・招待の既存契約を維持する。「認証なし・単一利用者・招待なし」は旧公開デモの仕様であり、今回の目標仕様ではない。

## 2. 飼い主入力とAI分析

以下の構造化項目を、フォーム、保存、AI入出力、Rules、validation、同意と安全境界へ一貫して追加する。保存しない入力欄を設けない。既存の `personality` / `playStyle` / `concerns` 自由記述との互換を維持する。選択肢と出典は [モック項目表](integration/pawpals-acceptance.md#モック項目と出典) を正とする。

| 分類 | 採用する項目 |
|---|---|
| 生殖関連 | 避妊・去勢、ヒート中か |
| 健康 | 混合ワクチン証明、狂犬病ワクチン、ノミ・ダニ予防、食物アレルギー、既往症・服薬、関節・視覚・聴覚の懸念 |
| 社会化歴 | 多頭飼い経験、ドッグラン・保育園、子犬期の社会化、過去のトラブル歴 |
| 行動6問 | 初対面の犬、遊び方、資源への反応、興奮の上がり方、落ち着くまで、苦手なことからの回復 |
| 7軸 | 外向性、社交性、神経質性、訓練性、資源防衛、自己主張、回復力 |

モックの「資源への反応」は「資源防衛」と同じ軸の表示名の揺れである。backendの先行確定契約では7軸は整数0〜100。構造化分析時は7軸必須で、AI分析とmatchingProfileへ同値保存しPetProfileへ伝搬する。旧5軸マッチングは互換継続し、旧データに7軸を捏造・補完しない。モックの固定値や文章を実AI結果として採用しない。

AIは入力の分析、根拠、信頼度の生成を担当する。全ペア採点・安全制約・最適化はTypeScriptの決定ロジックが担当する。7軸の追加だけを理由に既存配点や禁止条件を変更しない。

## 3. 登録の流れ

1. 施設ログイン後、選択スタッフが招待URL・QRを発行する。発行者の記録を維持する。
2. 飼い主が招待フォームへ入力し、分析対象と保存内容について同意する。
3. ブラウザが写真と動画由来の最大2枚のJPEGフレームを準備する。
4. ReactアプリからCloudflare Worker、OrcaRouterへ分析を依頼し、構造化結果を検証する。
5. 分析結果を含む受付を招待に紐づけてFirestoreへ保存する。施設側がプロフィールへ反映し、保存と読み戻しを確認する。
6. スタッフが日付と当日対象犬を明示選択・保存してから、部屋割り計算へ進む。

飼い主名・連絡先と元動画・音声はAI入力やログへ含めない。写真・動画原本を永続保存せず、媒体メタデータと分析結果を保存する。拡張した構造化項目のAI送信・同意・検証は同一契約で整備する。AIまたは保存失敗は明示エラーにし、固定結果や擬似成功へ切り替えない。

## 4. 当日対象と施設別部屋設定

- スタッフが対象日と当日対象犬を明示選択し、施設に紐づけて保存する。登録犬一覧をそのまま当日対象とみなさない。
- 相性計算と部屋割りはその選択対象だけで行う。n頭の全 `n(n-1)/2` ペアを採点してから最適化する。
- 施設別の部屋設定を永続化し、保存した設定を計算に使用する。定員、最低頭数、全頭配置、同室禁止を守る。
- 安全な解がなければ理由を表示する。手動での部屋割当編集は今回対象外。
- 対象日・対象犬・部屋設定と提案を関連付け、古い入力に基づく案を最新案として承認させない。

## 5. 提案・承認・却下・監査

| 起点 | 操作 | 結果・受入条件 |
|---|---|---|
| 当日対象・部屋設定 | 計算 | 対象に対する最新 `proposed` を保存 |
| 最新 `proposed` | 選択中スタッフが承認 | `confirmed`。承認者・時刻・理由・対象案を記録 |
| 最新 `proposed` | 却下 | `rejected`。担当・時刻・理由・対象案を記録 |
| 既存 `proposed` | 再計算で新案を保存 | 旧案を `superseded` とし、新案に元案参照を保持 |

承認対象は最新未確定案だけ。旧案を承認待ちへ重複集計しない。承認・却下・再計算は「誰が、いつ、何を、どの案に対して、どの理由で行ったか」を監査保存する。最終承認者は選択中スタッフであり、固定の名前や匿名オペレーターでは代用しない。

同時操作・再読込・保存失敗でも最新案と状態遷移が矛盾しないことを検証する。先行確定契約では日付別headとrevisionを用い、transactionで状態とappend-only監査を保存する。承認時は最新planId、対象日・対象revision・部屋revisionの一致を確認する（[ER図](ER図.md)）。実装・検証は進行中。基点のcreate-onlyなsnapshot Rulesだけではこの要件の完了とはしない。

## 6. 相性表示

scoreは%で表示する。既存 `EXPLICIT_BLOCK` などのハード制約と同室可否を明示し、数値の高さで禁止条件を上書きしない。定型の計算説明をAI生成説明と表示しない。

`GOOD / OK / CAUTION / AVOID / INCOMPATIBLE` の5分類と閾値は未確定のため追加しない。

## 7. 観測と将来カメラIF

スタッフの手動観測を入力・保存・表示・必要な再計算の実動線へ接続する。実在する `ObservationRecord` と保存済みsnapshotsを表示できる。

将来カメラ向けには入力源、operation event / observation ingestionの型、adapter境界と契約テストだけを定義する。カメラ接続、15分監視、映像保持、通知の実送信は今回対象外。実ログ、severity、alert ack、交流実績、架空アラートを生成しない。

## 8. 実装・検証・配備の扱い

基点には施設ログイン・招待隔離・既存6問の文字列化・5軸・全ペア計算・proposed/confirmed保存・手動観測経路がある。新しい健康/社会化/7軸、日付付き当日対象、施設別部屋設定、4状態遷移/監査、カメラIFはbackendとUIの単独実装・検証が完了し、App統合中である。統合typecheck、build、E2E、公開配備の証拠はまだない。

旧公開E2Eの34件/15件成功と、基点モック統合の46件/15件成功は異なる版の記録であり、今回要件の成功証拠に流用しない。基点モック統合はローカル検証で、公開配備していない。費用はFirebase Spark / Cloudflare Workers Freeに限定し、課金が必要なら停止する。
